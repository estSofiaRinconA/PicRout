PicRout — Guía de verificación manual del backend
Versión: 2.0 · Fecha: 2026-11-11
Ámbito: FastAPI, PostgreSQL Supabase, autenticación tradicional y Google, rutinas/rachas, IA por quiz.

IMPORTANTE: la verificación por fotos (single_photo/before_after) fue RETIRADA el 11/11/2026.
No probar endpoints /photo ni exigir evidencias fotográficas. La tienda, red social, notificaciones y cliente Android no se dan por implementados en esta guía.

0. ENTORNO
-----------
- Seleccionar rama correcta (desarrollo Google: feature/google-signin).
- Desde la carpeta backend: `python -m pip install -r requirements.txt`
- Archivo backend/.env con credenciales privadas del proyecto Supabase compartido.
- Ejecutar: `python -m uvicorn App.main:app --reload`
- Abrir http://127.0.0.1:8000/docs
- Nunca copiar tokens ni contraseñas a un informe público.

1. SALUD Y BASE DE DATOS
------------------------
[ ] GET /health -> HTTP 200.
[ ] Registrar usuario nuevo (ver sección 2).
[ ] Comprobar `username` nuevo en `public.users` mediante SQL Editor.
[ ] Reiniciar backend; login del mismo usuario continúa operativo.
NOTA: /health por sí solo no prueba conexión PostgreSQL.

2. AUTENTICACIÓN TRADICIONAL
---------------------------
POST /auth/register:
{
  "email": "prueba_documentacion@example.com",
  "username": "prueba_documentacion",
  "display_name": "Prueba Documentación",
  "password": "ClaveDePrueba2026!"
}
[ ] Respuesta de éxito (según esquema Swagger).
[ ] Correo y nombre de usuario duplicados rechazados, sin duplicar filas.

POST /auth/login:
{"identifier":"prueba_documentacion","password":"ClaveDePrueba2026!"}
[ ] 200 y access_token de PicRout.
[ ] Contraseña incorrecta -> 401.
[ ] GET /auth/me con autorización -> 200 y usuario correcto.
[ ] PUT /auth/me funciona según campos declarados en Swagger.
[ ] Solicitar OTP de recuperación (6 dígitos, un uso, 10 minutos), restablecer contraseña y rechazar reutilización.
NOTA: con SMTP no configurado puede ser modo desarrollo; no declarar envío real por correo sin comprobarlo.

3. GOOGLE SIGN-IN (SUPABASE AUTH)
---------------------------------
Requisitos externos: proveedor Google habilitado en el proyecto Supabase compartido; callback en Google Cloud; URL de retorno local autorizada para la prueba web; cuenta en Test users si aplica.

[ ] POST /auth/google pide `access_token`, no `id_token`.
[ ] {"access_token":"token_falso_de_prueba"} -> 401; no crea cuenta.
[ ] Página temporal de prueba OAuth en http://127.0.0.1:5500/google-test.html completa Google OAuth y obtiene sesión de Supabase.
[ ] POST /auth/google con el access_token **real de Supabase** -> 200 y JWT de PicRout.
[ ] Se creó cuenta en public.users con google_id no nulo y sin contraseña local.
[ ] Segundo POST /auth/google -> mismo ID, no crea duplicados.
[ ] Cuenta tradicional que coincide por correo -> 409 controlado; no vinculación automática.
[ ] Usuario desactivado -> 403 (pendiente de prueba si no hay caso autorizado).
[ ] Tokens expirados / proyecto equivocado -> rechazo (pendiente de prueba).
Nunca incluir tokens reales en informes ni usar la API `auth.users` como sustituto de `public.users`.

Consulta SQL solo lectura:
SELECT id, email, username, google_id
FROM public.users
WHERE google_id IS NOT NULL;

4. RUTINAS, OCURRENCIAS Y RACHA
------------------------------
Con autorización PicRout:
[ ] POST /routines crea rutina (nombre, descripción, días, hora, duración), revisar esquema Swagger.
[ ] GET /routines lista la nueva rutina.
[ ] GET /routines/{id} devuelve rutina creada.
[ ] PUT /routines/{id} modifica campos admitidos.
[ ] Desactivar rutina según endpoint actual: desaparece de listados activos y persiste.
[ ] GET /routines/today devuelve ocurrencias correspondientes al día.
[ ] GET /routines/streak devuelve estado coherente.
[ ] Completar una ocurrencia otorga puntos solo una vez.
[ ] Completar todas las ocurrencias del día permite actualizar racha.
[ ] Reevaluar mismo día NO repite racha ni bonus (idempotencia).

5. VERIFICACIÓN POR QUIZ
------------------------
[ ] POST /verification/analyze con nombre/descripcion -> método `quiz`, dificultad/puntos coherentes.
[ ] POST /verification/{occurrence_id}/start inicia intento quiz y cambia estado según API.
[ ] Responder mediante POST /verification/attempts/{attempt_id}/quiz con las respuestas esperadas por Swagger.
[ ] Aprobación según umbral configurado, actualización de ocurrencia y puntos.
[ ] Rechazo/resultado fallido del quiz se refleja correctamente.
[ ] GET /verification/attempts/{attempt_id} permite consultar resultado.
NO realizar pruebas de fotos: fueron eliminadas del proyecto.
